# Route 40 Motors — Service Booking & Aftersales Platform

An automotive aftersales application built on **SAP BTP ABAP Environment** with the **ABAP RESTful Application Programming Model (RAP)**, **CDS** and **SAP Fiori Elements**, plus an **AI booking summary** prototype.

Route 40 Motors models a multi-site car workshop. A customer's vehicle is booked for service, each booking reserves a spare part at a specific site, and the back end refuses the booking if that part is not in stock at that site. When a service is completed, the app takes the part out of stock under a lock and creates an invoice with a ZATCA-style QR code (TLV, Base64). The project also tracks parts deliveries and includes a Saudization (Nitaqat-style) workforce report with a hiring warning, reflecting the Saudi market it is themed on.

> Sample data in this repository is fictional.

## What it does

- **Service bookings**: list report and object page with create, edit and delete.
- **Stock validation**: a server-side validation (`checkStock`) blocks a booking when the part does not exist at the chosen site or is out of stock, on both create and edit. The rule lives in one class, `ZCL_STOCK_SERVICE`.
- **Input normalisation**: part, site and technician IDs are converted to upper case before validation, so `p001` and `P001` behave the same.
- **Complete Service action**: completes a booking, takes one part out of stock and creates an invoice record in `ZINVOICE` (net amount, 15% VAT, total in SAR). A completed booking cannot be completed again.
- **Stock locking**: the stock change runs inside a small action (`reserveOne`) on the spare part, under RAP's lock, so two users cannot take the last part.
- **Invoice QR code**: a ZATCA-style QR (TLV, Base64) is generated by `ZCL_ZATCA_TLV` and drawn on the booking object page.
- **Master data**: vehicles, sites, spare parts (stock is kept per part and per site), technicians.
- **Deliveries**: purchase-order quantity, delivered quantity and open quantity per delivery, with a *Receive Remaining* action.
- **Saudization report and hiring warning**: share of Saudi technicians per department with a colour band, and a warning when a new hire would lower a department's band.
- **AI booking summary** (prototype): a Python script that summarizes bookings and drafts customer reminders, with automated output checks. The in-app ABAP button is built but blocked on the trial. See [AI booking summary](#ai-booking-summary).

## Architecture

Every entity follows the same RAP layering:

```
Database table              ZSVCBOOKING, ZSPAREPART, ZVEHICLE, ZSITE, ZTECHNICIAN, ZDELIVERY, ZINVOICE
      |
Interface view  ZI_*        + behavior definition + behavior pool ZBP_I_* (validations, actions)
      |
Projection view ZC_*        + metadata extension ZME_* (Fiori list and object page layout)
      |
Service definition          ZSD_SVCBOOKING
      |
Service binding             ZSB_SVCBOOKING_V2  (OData V2 - UI)
      |
Fiori Elements app          List Report + Object Page (+ custom InvoiceQR section)
```

Supporting classes:

| Class | Purpose |
| --- | --- |
| `ZCX_ROUTE40` | Project exception class with a message text |
| `ZCL_STOCK_SERVICE` | One place that answers "is this part available at this site?" and returns stock, price and currency. Used by `checkStock` and `completeService`. Has ABAP Unit tests |
| `ZCL_SAUDI_BAND` | The Saudization band rule (cut-offs at 10, 20, 30 and 40 percent). Used by the technician warning. Has an ABAP Unit test |

## Stock validation (`checkStock`)

The validation runs on save. It asks `ZCL_STOCK_SERVICE` for the part at the booking's site. The service raises `ZCX_ROUTE40` when the row is missing or the quantity is below one, and the validation reports that text as an error on the booking.

```abap
" Simplified from the behavior pool ZBP_I_SVCBOOKING
LOOP AT bookings INTO DATA(booking).
  TRY.
      lo_stock->get_available_part(
        iv_part_id = booking-PartId
        iv_site_id = booking-SiteId ).
    CATCH zcx_route40 INTO DATA(lx_stock).
      " failed + reported: lx_stock->mv_text
  ENDTRY.
ENDLOOP.
```

## Complete Service and invoice QR

The *Complete Service* action finishes a booking, reduces the part's stock by one and writes an invoice to `ZINVOICE`. For example, a net amount of 22,000.00 SAR plus 15% VAT of 3,300.00 SAR gives a total of 25,300.00 SAR (invoice `INV-B015`).

The QR text is built by `ZCL_ZATCA_TLV` as a TLV structure (tag, length, value) and then Base64-encoded. The tags hold seller name, VAT registration number, timestamp, invoice total and VAT amount. The booking object page then draws the QR picture in a custom section (`InvoiceQR`) built with QRCode.js in an SAP Business Application Studio Fiori project.

## Locking the last part

**The problem.** Reading the stock with a plain SELECT and writing `stock - 1` later is a race. If one part is left and two users complete a service at the same moment, both read 1, both write 0, and the part is sold twice.

**The fix.** The stock change now lives in an action on the spare part, `reserveOne`. `ZI_SparePart` is the lock master, so RAP locks the part before the action runs. Inside the action the quantity is read again, checked, and reduced by one. `completeService` calls this action instead of writing the quantity itself.

```abap
" Simplified from ZBP_I_SPAREPART
METHOD reserveOne.
  READ ENTITIES OF zi_sparepart IN LOCAL MODE
    ENTITY SparePart FIELDS ( QtyStock )
    WITH CORRESPONDING #( keys ) RESULT DATA(parts).

  LOOP AT parts INTO DATA(part).
    IF part-QtyStock < 1.
      " failed + reported: Part is out of stock
      CONTINUE.
    ENDIF.
    MODIFY ENTITIES OF zi_sparepart IN LOCAL MODE
      ENTITY SparePart UPDATE FIELDS ( QtyStock )
      WITH VALUE #( ( %tky = part-%tky QtyStock = part-QtyStock - 1 ) ).
  ENDLOOP.
ENDMETHOD.
```

The action is not exposed in the projection view, so it has no button in the UI. It exists only for the application's own code.

## Saudization report and hiring warning

Saudization is Saudi Arabia's policy of raising the share of Saudi nationals in private-sector employment, and **Nitaqat** is the program that measures it and assigns companies a colour band. The report calculates, per department:

```
Saudization % = Saudi technicians / total technicians x 100
```

It is built as three stacked CDS view entities (counts, percentage, band), projected as `ZC_SaudiBand`, exposed as the `SaudiBand` entity, and shown in a Fiori Elements list report with criticality colours.

[![](https://github.com/Nishaweb-developer/ABAP_Route40_Motors/raw/main/screenshots/11-saudization-report.png)](https://github.com/Nishaweb-developer/ABAP_Route40_Motors/blob/main/screenshots/11-saudization-report.png)

**Important:** the bands (Red, Low Green, Mid Green, High Green, Platinum) use **illustrative cut-offs** (below 10, 20, 30 and 40 percent, then Platinum), not official Nitaqat thresholds. Real Nitaqat is calculated for a whole establishment, by sector and company size, not per department. The per-department view is a simplification for this demo.

### Hiring warning

When a technician is created, a validation (`warnSaudization`) compares the department's Saudization band before and after the hire. If the hire would move the department to a lower band, the user sees a **warning** and can still confirm the save. The band rule lives in `ZCL_SAUDI_BAND`, which has its own ABAP Unit test for the edge values.

```abap
" Simplified from ZBP_I_TECHNICIAN
DATA(lv_before) = CONV decfloat34( lv_saudi ) * 100 / lv_total.
DATA(lv_after)  = CONV decfloat34( lv_saudi + lv_new ) * 100 / ( lv_total + 1 ).

IF zcl_saudi_band=>band_of( lv_after ) < zcl_saudi_band=>band_of( lv_before ).
  " reported (warning): This hire lowers <department> from x% to y%
ENDIF.
```

## AI booking summary

This part of the project uses an LLM to summarize service bookings and draft customer reminders. It is an early experiment, built next to the core app. It is split into two parts:

| Part | Status |
| --- | --- |
| **Python prototype** (`route40-ai-assistant/`) | Working. Runs on exported SAP data, with automated output checks. |
| **ABAP version** (*Generate AI Summary* action in the Fiori app) | Built, but blocked. The app loads and shows the button, but the call to Gemini cannot run from the trial ABAP environment. |

### What the Python prototype does

1. Loads service bookings from `bookings.json` (exported from the Route 40 service).
2. For each booking, sends the record to Google Gemini with rules: use only the facts provided, write "not provided" for missing fields, never name a technician without a value, flag service/part mismatches, and write a customer reminder only for open bookings.
3. Retries automatically when Gemini is busy (`503`), waiting longer each time.
4. Runs checks on each answer and prints PASS or FAIL.

### What the AI checks found

- **Repeated data mismatch.** Booking B004 is an oil change with a brake pad set. The AI repeated both facts without flagging the mismatch. The second version of the prompt requires flagging it.
- **Lowercase booking ID.** `b028` was not flagged. The check failed, and the prompt now requires flagging it.
- **Internal labels in a customer reminder.** Booking B012's reminder included "Status: Open" and "Vehicle details: not provided", which should not reach a customer. The prompt now forbids this.

### Why the ABAP version is blocked

## Run it yourself

**SAP side**

1. Install the abapGit plugin in ADT and link this repository to a package in your ABAP Environment system, then **Pull**.
2. Activate all objects.
3. Run the seed classes (`ZCL_SEED_*`) with `F9` to load sample vehicles, sites, parts, bookings and technicians.
4. Open the service binding `ZSB_SVCBOOKING_V2`, publish it, select an entity (for example `SvcBooking`) and click **Preview**.
5. To run the tests, right-click the package and choose **Run As, ABAP Unit Test**.

**AI prototype (Python)**

```bash
pip3 install google-genai
export GEMINI_API_KEY="your-key-here"   # never commit this
cd route40-ai-assistant
python3 summarize.py
```

## Known limitations

- **Locking:** tested with two sessions (one held at a breakpoint), not load tested.
- **Authorization and draft handling:** not implemented yet.
- **Complete Service button:** it stays visible on a completed booking. The guard shows *Booking is already completed*, but the button should be disabled with instance feature control.
- **Hiring warning:** covers creating a technician only, not changing an existing one.
- **Texts:** messages are written directly in the code, so ATC reports them as untranslated. A message class is planned.
- **EML in loops:** `completeService` and the delivery action read and write inside loops. This is fine for one record at a time, but a bulk version should collect the changes first.
- **Tests:** class-level ABAP Unit tests exist. Behavior-level tests through EML are not written yet.
- Saudization bands are illustrative (see above).
- The invoice QR is for demonstration only (see scope note above).
- Some older Saudization rows (for example `Electrical` in mixed case) come from early test data and are counted as separate departments.
- **AI:** the Python prototype reads an exported file, not a live OData call. The ABAP AI button cannot reach Gemini on this trial (see [The ABAP side](#the-abap-side)).
- **AI:** the checks are pattern-based. A PASS means the basic rules held, not that the answer is correct.
- **AI:** Gemini's free tier has rate and daily limits, and returns `503` when busy.
